ArduPlane QuadPlane on the CoreWing F405 Wing APP V2. This package holds everything the team needs to program and configure each programmable part of the C0 lift + cruise VTOL, in the order the work is done. Every number has a source key; the full source list with check dates is in docs/research/firmware.md. Values marked (est.) are engineering estimates. "—" means the value is unknown.

Status, 2026-10-21. The parameter file passes the checker against the current ArduPlane metadata and the 4.7.1 stable metadata. All seven SITL scenarios passed on ArduPlane 4.7.2 (§11). Nothing here has run on the real board yet. Treat every gain as a starting value.

1. Install the tools (Windows)

  1. Mission Planner (primary ground station; parameter files, motor test, logs): installer firmware.ardupilot.org/Tools/MissionPlanner/MissionPlanner-latest.msi, guide ardupilot.org/planner/docs/mission-planner-installation.html.
  2. QGroundControl (optional second ground station): docs.qgroundcontrol.com/master/en/qgc-user-guide/getting_started/download_and_install.html. This package's parameter files use the Mission Planner/MAVProxy NAME,VALUE format. Load them with Mission Planner.
  3. STM32CubeProgrammer (needed once, for the first DFU flash): st.com/en/development-tools/stm32cubeprog.html. The ArduPilot page says it installs the DFU driver and may need Java (ardupilot.org/plane/docs/common-loading-firmware-onto-chibios-only-boards.html).
  4. ESC Configurator (web, Chrome/Edge): esc-configurator.com — BLHeli_S/Bluejay settings through the FC.
  5. ExpressLRS Configurator: github.com/ExpressLRS/ExpressLRS-Configurator/releases — receiver firmware and bind phrase.
  6. Python 3 + pymavlink for the tools in this folder: py -m pip install pymavlink. The checker uses only the standard library.

2. Firmware target and files

  • Target folder: firmware.ardupilot.org/Plane/stable/CoreWingF405WingV2
    • arduplane_with_bl.hex — bootloader plus firmware. First flash only, over DFU.
    • arduplane.apj — later updates from Mission Planner ("Install Firmware" > "Load custom firmware").
  • Do not use CoreWingF405WMiniV2. That target is for the Wing Mini V2, which has a different current-sensor scale (BATT_AMP_PERVLT 51 vs 64, board page).
  • Pin the firmware version for the season. Record ArduPlane V4.7.2 (git hash) from the Mission Planner Messages tab in the build log. Retest in SITL before any upgrade.

3. First flash (DFU)

The board ships without an ArduPilot bootloader (hwdef README "Loading Firmware").

  1. Remove the props. Unplug the flight battery. Leave only USB connected.
  2. Enter DFU mode. The board has no boot button. The hwdef README says to "pull the BOOT0 pin on the USB extender connector low while powering the board over USB, or hold the BOOT button on the wireless USB extender module if one is fitted". The included wireless module has that BOOT button, so use it. (On STM32 parts, BOOT0 is normally pulled high for DFU. The extender may invert it. Check the CoreWing Wing V2 user manual linked from the ArduPilot board page before bridging any pin.)
  3. In Device Manager, check for "STM32 BOOTLOADER" under Universal Serial Bus devices.
  4. STM32CubeProgrammer: connection USB > Connect > Open file arduplane_with_bl.hex > Download.
  5. Power-cycle. In Mission Planner, connect over USB (COM port, 115200, or auto). Messages should show ArduPlane V4.7.2 and the board name.
  6. Later updates: Mission Planner > Setup > Install Firmware > "Load custom firmware" > arduplane.apj (or pick Plane from the list once the board is detected).

4.3 Airspeed sensor: I²C address: MS5525DSO must run at 0x77

The BOM buys the Holybro MS5525DSO + PT40 (BOM line "Holybro MS5525DSO + PT40 airspeed"). Holybro's product page gives its I²C address as 0x76 (holybro.com/products/digital-air-speed-sensor-standard, 2026-10-21). That is the address of this board's SPL06 barometer, which sits on the same and only I²C bus (hwdef BARO SPL06 I2C:0:0x76, I2C_ORDER I2C1). Two devices cannot share an address on one bus.

The MS5525DSO has two addresses. The TE datasheet says "MS5525DSO address is 111011Cx, where C is the complementary value of the pin CSB" (farnell.com/datasheets/2722597.pdf, checked 2026-10-21): CSB high → 0x76, CSB low → 0x77. The ArduPilot driver probes both (AP_Airspeed_MS5525.cpp: 0x76, 0x77), and ARSPD_TYPE can pin one: 3 = auto, 4 = 0x76, 5 = 0x77 (apm.pdef.xml).

Setting used: ARSPD_TYPE,5 (MS5525 at 0x77), ARSPD_BUS,0. Forcing 0x77 also stops the driver from probing 0x76, where it would find the barometer. Hardware step required:

  1. On the Holybro breakout, find the MS5525DSO CSB pin (pin assignment in the TE datasheet). Re-strap it from VDD to GND: lift the pull-up or cut the trace, then bridge to GND. Whether the Holybro PCB has a jumper or solder bridge for this: — (inspect the board when it arrives; photograph it for the build log).
  2. Bench check: power the FC on USB with only the airspeed sensor on I²C. Mission Planner Messages must show MS5525[0]: Found on bus 0 addr 0x77 (driver text). The barometer must still read altitude (HUD). If the message shows 0x76, or the baro reads nonsense, the strap is wrong. Do not fly.
  3. Blow gently into the pitot: airspeed must rise. Then do the offset calibration (§6.8).

Fallback if the re-strap is not practical: buy Holybro MS4525DO sensor-only (SKU 19007, $46.59) + PT40 pitot-only (SKU 32022, $7.99) = $54.58, address 0x28, and set ARSPD_TYPE,1. That is $5.41 below the MS5525DSO/PT40 kit at $59.99 (holybro.com product JSON, 2026-10-21). Whether the sensor-only kit includes cable and tubing: —.

5. Load the parameters

  1. Validate first: py firmware/tools/check_params.py firmware/vtol_c0.param --corewing --require-every-line-commented.
  2. Mission Planner > Config > Full Parameter List > Load from file > vtol_c0.param > Write Params.
  3. Reboot. Q_ENABLE and the DShot settings (Q_M_PWM_TYPE, SERVO_BLH_*) take effect only after a reboot, and the Q_ parameters do not exist until then.
  4. Load the same file a second time, Write Params, and reboot again. Then use "Compare Params" against the file: every row should match.
  5. Hover-only sessions: also load vtol_c0_hover_phase.param. Reload vtol_c0.param before the first transition session.
  6. Save the full parameter list (Save to file) after each session as params_<date>.param in the team log.

  • Wrong direction: swap two of the three motor phase wires, or reverse it in ESC Configurator (peripherals.md §1).
  • With the props on and the aircraft tethered, find the lowest test % that spins all four cleanly → Q_M_SPIN_ARM. The lowest that gives a little thrust → Q_M_SPIN_MIN (quadplane-vtol-tuning-process.html step 4).

9. First-flight build-up

Fly at a site that allows the test (review §15). Hover tests: ≤ 5 m AGL, ≤ 60 s per hover (review §12, R14). Transitions: ≥ 30 m AGL, into wind. Wind ≤ 5 m/s, gusts ≤ 8 m/s (R16). The full checklists are in checklists.md.

9.1 SITL rehearsal (every pilot, before any flight)

Run sitl/mission_test.py (see sitl/README.md). Then fly the same SITL by hand from Mission Planner's simulator with the Pocket Crush as a USB joystick: QSTABILIZE take-off, QLOITER, FBWA transition, CRUISE, QLOITER back-transition, QLAND. Practise the E-stop and RTL switches.

9.2 Tethered bench run

Props on, aircraft tied down to a heavy base, battery on, vtol_c0_hover_phase.param loaded. QSTABILIZE, arm, raise throttle to light the skids. Check for oscillation, vibration and current (≈ 37.5 A hover at full weight; results.json C0.sized.I_hover).

9.3 First lift-off (QSTABILIZE): tuning-process steps 5–6

  1. Arm, disarm at once (proves the disarm path), arm again.
  2. Raise the throttle slowly. At lift-off, set it straight back down. Disarm and look for oscillation.
  3. If it oscillated: reduce Q_A_RAT_RLL_P/I/D and Q_A_RAT_PIT_P/I/D by 50 % and repeat (tuning-process step 6).
  4. Hover at about 1 m and give 5° roll/pitch inputs. Land at any oscillation.

9.4 QHOVER, hover throttle, notch

  1. Take off in QSTABILIZE to 5 m, switch to QHOVER for ≥ 30 s with no inputs. Q_M_HOVER_LEARN,2 saves the hover throttle. Expect about 0.49 (est.) from 1545.6 g needed / 3130 g max per motor (results.json). Above 0.6 means the thrust margin is short (tuning-process step 7, "should be ~0.3–0.6").
  2. Then set Q_P_D_ACC_P = 0.1 × Q_M_THST_HOVER and Q_P_D_ACC_I = 0.2 × Q_M_THST_HOVER (tuning-process step 7).
  3. Notch setup within the 60 s hover limit. The tuning-process page asks for a 2-minute no-input hover. The review limits test hovers to 60 s (R14 mitigation). Two other ArduPilot sources cover the shorter hover:
    • The batch-sampler page asks for "a regular flight (not just a gentle hover) of at least 1 minute" (common-imu-batchsampling.html). One 60 s QHOVER with INS_LOG_BAT_MASK,1 and INS_LOG_BAT_OPT,4 (pre + post filter, both already set) meets that.
    • Throttle-based notch tracking needs only the hover noise frequency and the hover thrust. Hover-thrust learning needs "no pilot stick input for at least 10 seconds" (same page; Q_M_HOVER_LEARN,2).
    • Procedure: fly two separate 60 s no-input QHOVER flights on a calm day. Open each .BIN in firmware.ardupilot.org/Tools/WebTools/FilterReview (or Mission Planner > Setup > Advanced > FFT > "IMU Batch Sample"). Accept the peak only if both flights agree within about 10 % (est.); the average is hover_freq. More batches per flight are available by lowering INS_LOG_BAT_LGIN (batch page: "can be lowered to increase accuracy").
    • Set the throttle-based notch (common-throttle-based-notch.html): INS_HNTCH_ENABLE,1, reboot, INS_HNTCH_MODE,1, INS_HNTCH_FREQ = hover_freq, INS_HNTCH_BW = hover_freq/2, INS_HNTCH_REF = learned Q_M_THST_HOVER. Leave INS_HNTCH_HMNCS at its default 3 (1st + 2nd harmonic). The in-flight FFT auto-setup is not available (!HAL_GYROFFT_ENABLED).
    • Fly one more 60 s hover and check that the post-filter spectrum shows the peak attenuated. Then set INS_LOG_BAT_MASK,0 to free RAM (batch page note).
  4. Then QLOITER: position hold within about 2 m in light wind (est.).
  5. Manual roll/pitch tune, then QAUTOTUNE (in the build) per tuning-process steps 10+ and qautotune-mode.html.

9.5 Fixed-wing preparation

  • Airspeed ratio: ARSPD_AUTOCAL,1 for a 5-minute loiter, then back to 0 (calibrating-an-airspeed-sensor.html). Review M12.1 failure threshold: > 10 % error puts the real transition speed under R11's 15.6 m/s.
  • Fixed-wing gains start at firmware defaults. Run AUTOTUNE in FBWA after the first transitions (automatic-tuning-with-autotune.html).

9.6 First transitions

  1. Load vtol_c0.param again (removes the hover-phase overlay). Check Q_ASSIST_SPEED = 13.
  2. QLOITER to ≥ 30 m, nose into wind, with the longest clear line ahead.
  3. Switch to FBWA and push the throttle to about 70 %. The lift motors hold height. At AIRSPEED_MIN 16 m/s they taper out over 5 s. In SITL this took 10–11 s from mode change to "Transition done" (sitl/results).
  4. Start the turn as soon as "Transition done" appears. In SITL, a straight FBWA transition reached the 300 m fence circle about 6 s after transition end (first SITL run, scenario B, 2026-10-21). Start transitions from the upwind edge of the field.
  5. Back-transition: select QLOITER (or QHOVER). The pusher stops at once and the lift motors brake the aircraft (quadplane-transitions.html). Allow about 100 m stopping distance at 20 m/s (2 m/s² decel).
  6. Check in the log: the transition current peak against the 74.4 A estimate (results.json C0.sized.I_trans), battery sag, and time to AIRSPEED_MIN. Review M12.2 failure threshold: > 15 s or > 100 m.
  7. Only then: CRUISE circuits, RTL test at altitude, and the full R9 mission in AUTO (sitl/mission_test.py scenario A is the template: NAV_WAYPOINTs then NAV_VTOL_LAND).

10. Decisions that changed the review's controls chapter

Details and rationale are in docs/research/firmware.md. They should be folded into the review:

  1. Output map: lift on S5–S8, pusher S9, rudder 2 on S11 (DShot timer-group conflict in the review map).
  2. Airspeed sensor: the MS5525DSO ships at 0x76, the onboard baro's address. Run it at 0x77 (CSB strapped low, ARSPD_TYPE,5) or swap to MS4525DO (§4.3). The review row "I²C MS5525DSO airspeed" needs this note.
  3. Telemetry (no radio in the BOM, $0): one RP3 V2 runs either CRSF or ELRS-MAVLink, not both (review row "CRSF + MAVLink"). Baseline for hover phases: CRSF (SERIAL6_PROTOCOL,23), with telemetry on the Pocket Crush. GCS link for transition flights: ELRS MAVLink mode (SERIAL6_PROTOCOL,2, SERIAL6_BAUD,460, RSSI_TYPE,5, ELRS ≥ 3.5 on TX and RX, Mission Planner on UDP 14550 via the Pocket Crush backpack WiFi). The RX then sends RC as RC_CHANNELS_OVERRIDE; SITL scenario G showed RC-loss failsafe 1 s after the overrides stop. Details and limits: peripherals.md §2.3–2.4.
  4. Transition threshold: the state diagram labels say "≥ 15 m/s" and "< 12 m/s". The table says AIRSPEED_MIN 16 and Q_ASSIST_SPEED 13. The parameters use 16 and 13.
  5. Battery current limit: BATT_WATT_MAX is not in this build. Q_M_BAT_CURR_MAX limits only the lift motors, so it is set to 85 A as a fault guard, not 60 A. Transition current is managed with TKOFF_THR_MAX 75 % and the pilot's throttle. Bench test M4 decides.
  6. Low-battery action, two stages: low (30 % / 1950 mAh, or 21.0 V sag-compensated) → RTL, which ends in QRTL and a vertical landing at home (Q_RTL_MODE,1). Critical (20 % / 1300 mAh, or 19.8 V) → QLAND in place. ArduPilot's failsafe page calls "BATT_FS_LOW_ACT = 1 (RTL) and BATT_FS_CRT_ACT = 2 (Land)" a reasonable setup. 4 = QLand is used for the explicit VTOL landing. The review had low = QLAND. The hover-phase overlay sets low → QLAND, because RTL would start a fixed-wing return. (Note: the parameter is BATT_FS_LOW_ACT; BATT_FS_LLOW_ACT does not exist.)
  7. Fence ceiling: 110 m above home, 12 m below the 400 ft (121.9 m) limit, so the climb overshoot after a breach stays legal. SITL peaked at 113.1 m, 3.1 m over the fence. Review wording: "fence 110 m, 12 m below the 400 ft limit".
  8. RC loss in hover: QLAND in place (ArduPilot behaviour in Q modes). The review's "RC loss → RTL then QLAND" applies to fixed-wing modes only.
  9. Firmware: stable 4.7.2 now covers the CoreWing. The 2027-02-22 go/no-go can close early.

11. SITL validation summary (2026-10-21)

ArduPlane V4.7.2 SITL (the Windows build Mission Planner uses, from firmware.ardupilot.org/Tools/MissionPlanner/sitl/PlaneStable), model quadplane, vtol_c0.param + sitl/sitl_overrides.param. 133 parameters read back. All match. Only the 3 BLHeli passthrough parameters (SERVO_BLH_*) are absent, because SITL has no BLHeli support. 7/7 scenarios passed. Results and limits are in sitl/README.md. The SITL airframe is ArduPilot's generic QuadPlane model, not C0. Its learned hover throttle was 0.15, against about 0.49 (est.) for C0. So SITL validates modes, thresholds, failsafes and the fence.
